# Flash Sale Module — System Design
### Java / Spring Boot / H2 (test) / MySQL or Postgres (prod)

---

## 1. Problem Statement

A flash sale exposes a very small stock of items to a very large burst of concurrent buyers for a short time window. The module must:

- **Never oversell** — sold quantity must never exceed configured stock, even under thousands of concurrent requests.
- **Never lose a legitimate sale** — a successful reservation must reliably become an order.
- **Prevent duplicate orders** — one user should not be able to grab N units via double-clicks, retries, or multiple tabs.
- **Auto-release abandoned reservations** — if a user reserves stock but doesn't pay in time, stock returns to the pool.
- **Stay responsive under load** — reject fast (fail fast) rather than queue everyone against the database.

**Design principle:** the database is the single source of truth for stock counts (H2/MySQL row-level locking gives us correctness for free). Redis is an optional accelerator for read-heavy "is this sale live / how much stock" checks and for cross-instance idempotency locks once you scale beyond one app instance — it is not required for correctness in a single-node/H2 setup.

## 3. Core Domain Model

| Entity | Purpose |
|---|---|
| `FlashSaleEvent` | A time-boxed sale window (start/end time, status) |
| `FlashSaleItem` | A product entered into a sale, with `totalStock`, `reservedStock`, `soldStock`, `version` |
| `InventoryReservation` | A short-lived hold on N units for one user/order, with `expiresAt` |
| `Order` | The commercial record, states: `PENDING_PAYMENT → PAID → CANCELLED/EXPIRED` |
| `OrderItem` | Line item linking order to flash sale item + quantity + price snapshot |
| `IdempotencyKey` | Dedupe table so retried requests don't double-reserve |

### 3.1 Schema (DDL, works identically on H2 and MySQL)

```sql
CREATE TABLE flash_sale_event (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    name          VARCHAR(255) NOT NULL,
    start_time    TIMESTAMP NOT NULL,
    end_time      TIMESTAMP NOT NULL,
    status        VARCHAR(20) NOT NULL DEFAULT 'SCHEDULED' -- SCHEDULED, ACTIVE, ENDED
);

CREATE TABLE flash_sale_item (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    event_id        BIGINT NOT NULL REFERENCES flash_sale_event(id),
    product_id      BIGINT NOT NULL,
    sale_price      DECIMAL(12,2) NOT NULL,
    total_stock     INT NOT NULL,
    reserved_stock  INT NOT NULL DEFAULT 0,
    sold_stock      INT NOT NULL DEFAULT 0,
    per_user_limit  INT NOT NULL DEFAULT 1,
    version         BIGINT NOT NULL DEFAULT 0,           -- optimistic lock
    CONSTRAINT chk_stock CHECK (reserved_stock + sold_stock <= total_stock)
);

CREATE TABLE inventory_reservation (
    id               BIGINT AUTO_INCREMENT PRIMARY KEY,
    flash_sale_item_id BIGINT NOT NULL REFERENCES flash_sale_item(id),
    user_id          BIGINT NOT NULL,
    order_id         BIGINT,
    quantity         INT NOT NULL,
    status           VARCHAR(20) NOT NULL DEFAULT 'HELD', -- HELD, CONFIRMED, RELEASED, EXPIRED
    created_at       TIMESTAMP NOT NULL,
    expires_at       TIMESTAMP NOT NULL
);

CREATE TABLE orders (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id       BIGINT NOT NULL,
    status        VARCHAR(20) NOT NULL DEFAULT 'PENDING_PAYMENT',
    total_amount  DECIMAL(12,2) NOT NULL,
    created_at    TIMESTAMP NOT NULL,
    expires_at    TIMESTAMP NOT NULL
);

CREATE TABLE order_item (
    id                  BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_id            BIGINT NOT NULL REFERENCES orders(id),
    flash_sale_item_id  BIGINT NOT NULL REFERENCES flash_sale_item(id),
    quantity            INT NOT NULL,
    unit_price          DECIMAL(12,2) NOT NULL
);

CREATE TABLE idempotency_key (
    request_key   VARCHAR(100) PRIMARY KEY,
    user_id       BIGINT NOT NULL,
    order_id      BIGINT,
    created_at    TIMESTAMP NOT NULL
);

-- one active reservation per user per item avoids duplicate grabs
CREATE UNIQUE INDEX ux_reservation_user_item_active
    ON inventory_reservation(flash_sale_item_id, user_id)
    WHERE status = 'HELD'; -- (H2/Postgres partial index; on MySQL enforce in app layer + unique key workaround)
```

## 4. The Hard Part: Concurrency-Safe Inventory Reservation

Three viable strategies, in increasing order of scale:

### Option A — Atomic conditional UPDATE (recommended starting point)
No explicit locking needed; rely on the database's row-level atomicity.

```sql
UPDATE flash_sale_item
SET reserved_stock = reserved_stock + :qty,
    version = version + 1
WHERE id = :itemId
  AND (total_stock - reserved_stock - sold_stock) >= :qty;
```

If the `UPDATE` affects **0 rows**, stock was insufficient — reject immediately. This single statement is atomic in both H2 and MySQL/Postgres; no race window exists between "check stock" and "decrement stock" because the check is embedded in the `WHERE` clause of the write itself.

### Option B — JPA Optimistic Locking (`@Version`)
Good when you're already loading the entity via JPA and want to reuse `@Transactional` retry semantics. On `OptimisticLockException`, retry with backoff (bounded, e.g. 3 attempts) — cheap under low contention, wasteful under a true flash-sale stampede (thousands hitting one row) because most attempts fail and retry.

### Option C — Pessimistic row lock (`SELECT ... FOR UPDATE`)
Serializes all writers on the hot row. Simpler mental model, but throughput is capped by lock hold time. Fine for moderate flash sales; for extreme (e.g. 100k req/s on one SKU) you'd typically pre-shard the stock counter (e.g. split 1,000 units into 10 counters of 100 and route users by hash) or move the hot counter into Redis (`DECR` / Lua script) and only touch the RDBMS asynchronously for the durable order record.

**This design uses Option A as the default** (best correctness/throughput tradeoff without new infra), with a note on evolving to Redis counters if you outgrow single-row throughput.

## 5. Request Flow (happy path)

```
1. User clicks "Buy" → client sends idempotency-key + itemId + qty
2. Controller checks rate limit (per-user token bucket)
3. Check idempotency_key table — if key exists, return the prior result (no double action)
4. Verify sale is ACTIVE (start_time <= now <= end_time)
5. Verify user hasn't exceeded per_user_limit (existing HELD/CONFIRMED reservations)
6. Atomic conditional UPDATE on flash_sale_item (reserve stock)  -- Option A above
      -> if 0 rows affected: return 409 SOLD_OUT
7. Insert inventory_reservation (status=HELD, expires_at = now + 5 min)
8. Create Order (status=PENDING_PAYMENT, expires_at = now + 5 min)
9. Store idempotency_key -> order_id
10. Return order to client with countdown timer for payment
```

### Payment confirmation
```
1. Payment webhook/callback arrives for order_id
2. Transactionally:
   - orders.status = PAID
   - inventory_reservation.status = CONFIRMED
   - flash_sale_item.sold_stock += qty ; reserved_stock -= qty
```

### Expiry sweep (scheduled job, every N seconds, or a delayed queue message per reservation)
```
1. Find inventory_reservation WHERE status='HELD' AND expires_at < now
2. Transactionally:
   - reservation.status = EXPIRED
   - flash_sale_item.reserved_stock -= qty
   - order.status = EXPIRED (if still PENDING_PAYMENT)
```
Using a message-queue delayed message (per reservation, TTL = hold duration) scales better than a polling sweep once reservation volume is high, since the sweep avoids scanning a growing table. Both are shown below; start with the scheduler for simplicity.

### 6.2 Repository — the atomic conditional reserve

```java
public interface FlashSaleItemRepository extends JpaRepository<FlashSaleItem, Long> {

    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("""
        UPDATE FlashSaleItem f
        SET f.reservedStock = f.reservedStock + :qty,
            f.version = f.version + 1
        WHERE f.id = :itemId
          AND (f.totalStock - f.reservedStock - f.soldStock) >= :qty
    """)
    int tryReserve(@Param("itemId") Long itemId, @Param("qty") int qty);

    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("""
        UPDATE FlashSaleItem f
        SET f.reservedStock = f.reservedStock - :qty
        WHERE f.id = :itemId
    """)
    int releaseReservedStock(@Param("itemId") Long itemId, @Param("qty") int qty);

    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("""
        UPDATE FlashSaleItem f
        SET f.reservedStock = f.reservedStock - :qty,
            f.soldStock = f.soldStock + :qty
        WHERE f.id = :itemId
    """)
    int confirmSale(@Param("itemId") Long itemId, @Param("qty") int qty);
}
```

### 6.3 Service — reservation with idempotency + per-user limit

```java
@Service
public class FlashSaleService {

    private final FlashSaleItemRepository itemRepo;
    private final InventoryReservationRepository reservationRepo;
    private final OrderRepository orderRepo;
    private final IdempotencyKeyRepository idemRepo;

    private static final Duration HOLD_DURATION = Duration.ofMinutes(5);

    @Transactional
    public ReserveResult reserve(Long userId, Long itemId, int qty, String idempotencyKey) {

        // 1. idempotency short-circuit
        idemRepo.findById(idempotencyKey).ifPresent(existing -> {
            throw new DuplicateRequestException(existing.getOrderId());
        });

        FlashSaleItem item = itemRepo.findById(itemId)
                .orElseThrow(() -> new NotFoundException("item not found"));

        // 2. per-user limit check
        int alreadyHeld = reservationRepo.sumActiveQuantityForUser(itemId, userId);
        if (alreadyHeld + qty > item.getPerUserLimit()) {
            throw new LimitExceededException();
        }

        // 3. atomic conditional reserve — the correctness-critical line
        int updated = itemRepo.tryReserve(itemId, qty);
        if (updated == 0) {
            throw new SoldOutException();
        }

        // 4. persist reservation + pending order
        InventoryReservation reservation = new InventoryReservation();
        reservation.setFlashSaleItemId(itemId);
        reservation.setUserId(userId);
        reservation.setQuantity(qty);
        reservation.setStatus(ReservationStatus.HELD);
        reservation.setCreatedAt(LocalDateTime.now());
        reservation.setExpiresAt(LocalDateTime.now().plus(HOLD_DURATION));
        reservationRepo.save(reservation);

        Order order = new Order();
        order.setUserId(userId);
        order.setStatus(OrderStatus.PENDING_PAYMENT);
        order.setTotalAmount(item.getSalePrice().multiply(BigDecimal.valueOf(qty)));
        order.setCreatedAt(LocalDateTime.now());
        order.setExpiresAt(LocalDateTime.now().plus(HOLD_DURATION));
        orderRepo.save(order);

        reservation.setOrderId(order.getId());

        idemRepo.save(new IdempotencyKey(idempotencyKey, userId, order.getId(), LocalDateTime.now()));

        return new ReserveResult(order.getId(), reservation.getExpiresAt());
    }
}
```

> Note: `tryReserve` runs its own atomic `UPDATE`, so even though the surrounding method is `@Transactional`, there's no read-then-write race — the WHERE clause enforces the invariant at the database level regardless of how many threads enter concurrently.

### 6.4 Expiry sweeper

```java
@Component
public class ReservationExpiryJob {

    private final InventoryReservationRepository reservationRepo;
    private final FlashSaleItemRepository itemRepo;
    private final OrderRepository orderRepo;

    @Scheduled(fixedDelay = 5000)
    @Transactional
    public void releaseExpiredReservations() {
        List<InventoryReservation> expired =
            reservationRepo.findByStatusAndExpiresAtBefore(ReservationStatus.HELD, LocalDateTime.now());

        for (InventoryReservation r : expired) {
            itemRepo.releaseReservedStock(r.getFlashSaleItemId(), r.getQuantity());
            r.setStatus(ReservationStatus.EXPIRED);
            orderRepo.findById(r.getOrderId()).ifPresent(o -> {
                if (o.getStatus() == OrderStatus.PENDING_PAYMENT) {
                    o.setStatus(OrderStatus.EXPIRED);
                }
            });
        }
    }
}
```

### 6.5 Controller

```java
@RestController
@RequestMapping("/api/flash-sale")
public class FlashSaleController {

    @ExceptionHandler(LimitExceededException.class)

    }
}
```

### 7.1 The concurrency test that matters most

This is the test that actually proves "no overselling" — spin up N threads hammering one item with total demand > stock:

```java
@SpringBootTest
@ActiveProfiles("test")
class FlashSaleConcurrencyTest {

    @Autowired FlashSaleService service;
    @Autowired FlashSaleItemRepository itemRepo;

    @Test
    void shouldNeverOversell() throws InterruptedException {
        FlashSaleItem item = new FlashSaleItem();
        item.setTotalStock(50);
        item.setReservedStock(0);
        item.setSoldStock(0);
        item.setPerUserLimit(1);
        item.setSalePrice(BigDecimal.TEN);
        item = itemRepo.save(item);
        Long itemId = item.getId();

        int users = 500; // 500 users racing for 50 units
        ExecutorService pool = Executors.newFixedThreadPool(50);
        CountDownLatch latch = new CountDownLatch(users);
        AtomicInteger successCount = new AtomicInteger();

        for (long u = 0; u < users; u++) {
            long userId = u;
            pool.submit(() -> {
                try {
                    service.reserve(userId, itemId, 1, "key-" + userId);
                    successCount.incrementAndGet();
                } catch (SoldOutException ignored) {
                } finally {
                    latch.countDown();
                }
            });
        }
        latch.await(30, TimeUnit.SECONDS);

        assertThat(successCount.get()).isEqualTo(50);
        FlashSaleItem finalItem = itemRepo.findById(itemId).orElseThrow();
        assertThat(finalItem.getReservedStock() + finalItem.getSoldStock()).isEqualTo(50);
    }
}
```

If this test ever fails intermittently, it means the reservation path regressed to a read-then-write race — treat it as a release blocker.

## 8. Handling Scale Beyond a Single DB Row

Once one SKU's row becomes the bottleneck (thousands of writes/sec against one row), evolve in this order:

1. **Cache the "is sold out" read** in Redis so the 99% of requests arriving after sellout never touch the DB at all (`GET soldout:{itemId}` fast-path before attempting the SQL update).
2. **Move the hot counter into Redis** with a Lua script (`DECR`-if-positive is atomic in Redis) and treat Redis as the reservation authority; asynchronously persist confirmed reservations into the RDBMS via a queue for durability/audit. Reconcile on startup.
3. **Shard the counter**: split `total_stock` into K sub-counters (K partitions of the row, or K keys in Redis), route each user deterministically (hash of userId) to one shard, and only fall back to scanning other shards if their assigned shard is empty. Reduces contention on any single row/key.
4. **Queue-based admission control**: put requests into a queue (Kafka) and process reservations sequentially per item by a single consumer — trades latency for guaranteed correctness without any locking at all, and naturally implements "first come, first served."

## 9. Additional Safeguards Worth Calling Out

- **Rate limiting** at the gateway (per-IP and per-user token bucket) so bot traffic doesn't drown the DB before it even reaches the reservation logic.
- **Idempotency keys** are mandatory on the reserve endpoint — mobile clients retry on timeout, and without this a slow response can cause a duplicate reservation.
- **Per-user purchase limit** enforced at the DB layer too (unique partial index shown in §3.1), not just in application code, since app-layer checks alone have the same race condition as stock checks.
- **Clock skew**: use DB server time (`NOW()`/`CURRENT_TIMESTAMP`) for sale-window checks, not application server time, to avoid multi-instance drift opening the sale early on one node.
- **Warm-up / pre-heating**: pre-load the flash sale item row into the connection pool's cache and consider `SELECT` pinning it in buffer pool before the sale starts, since the very first burst of traffic at T=0 is the worst spike.
- **Observability**: emit metrics on reservation success/fail rate, sellout time, and reservation-to-payment conversion — these numbers tell you if the hold duration is too generous (inventory sitting reserved-but-unpaid) or too short (legitimate buyers losing their cart).

## 10. Summary of State Transitions

```
FlashSaleItem stock:      available = total - reserved - sold

Order:        PENDING_PAYMENT ──pay──▶ PAID
                     │
                     └──timeout/cancel──▶ EXPIRED / CANCELLED

Reservation:   HELD ──payment confirmed──▶ CONFIRMED
                 │
                 └──timeout──▶ EXPIRED  (stock released back to available)
```

This gives you: no overselling (atomic conditional UPDATE), no duplicate orders (idempotency key + unique active-reservation index), no permanently locked stock (expiry sweeper), and a clear upgrade path (Redis counters, sharding, queue-based admission) if a single SKU's traffic outgrows what one database row can serialize.
