# Flash Sale Module — Test Cases

Reference: `flash-sale-system-design.md`. Covers functional, concurrency, idempotency, timing, and edge-case scenarios for the reservation → order → payment → expiry flow.

## 1. Sale Window / Eligibility

| ID | Title | Preconditions | Steps | Expected Result |
|---|---|---|---|---|
| TC-01 | Reserve before sale starts | Event `start_time` is in the future | Call reserve endpoint for an item in that event | Request rejected, e.g. `403 SALE_NOT_STARTED`; no reservation row created |
| TC-02 | Reserve after sale ends | Event `end_time` is in the past | Call reserve endpoint | Request rejected, e.g. `410 SALE_ENDED`; no reservation row created |

| TC-05 | Sale window uses DB time, not app server time | App server clock skewed ±30s from DB clock | Attempt reserve just before/after boundary per DB clock | Behavior matches DB clock, not app clock |

## 3. Per-User Purchase Limit

| ID | Title | Preconditions | Steps | Expected Result |
|---|---|---|---|---|
| TC-16 | User reserves up to their limit | `perUserLimit=2`, user has 0 active reservations | Reserve qty=2 in one call | Succeeds |
| TC-17 | User exceeds limit in a single request | `perUserLimit=2` | Reserve qty=3 | Rejected `429 PER_USER_LIMIT_EXCEEDED`; stock unchanged |
| TC-18 | User exceeds limit across multiple requests | `perUserLimit=1`; user already has 1 `HELD` reservation | Reserve qty=1 again | Rejected `429 PER_USER_LIMIT_EXCEEDED` |
| TC-19 | Limit check ignores expired/released reservations | `perUserLimit=1`; user's prior reservation is `EXPIRED` | Reserve qty=1 | Succeeds (expired reservations don't count toward limit) |
| TC-20 | Limit check ignores cancelled orders' reservations | `perUserLimit=1`; user's prior reservation `RELEASED` due to order cancellation | Reserve qty=1 | Succeeds |
| TC-21 | Two different users each hit their own limit independently | `perUserLimit=1` | User A reserves 1, User B reserves 1 | Both succeed independently; combined stock deducted correctly |
| TC-22 | Concurrent requests from same user racing the limit check | `perUserLimit=1` | Fire 10 simultaneous reserve calls from same user, same item | Exactly 1 succeeds; 9 rejected with `PER_USER_LIMIT_EXCEEDED` or `SOLD_OUT`; DB-level unique constraint (not just app logic) enforces this |

## 4. Idempotency

| ID | Title | Preconditions | Steps | Expected Result |
|---|---|---|---|---|
| TC-23 | Duplicate request with same idempotency key returns original result | User successfully reserved with key `K1` | Repeat identical request with key `K1` | Returns the same `orderId` as before; no new reservation or order created; stock not double-decremented |
| TC-24 | Duplicate key from a different user | Key `K1` already used by User A | User B sends request with key `K1` | Rejected or returns User A's order per idempotency-key semantics (documented behavior: keys are global, not per-user) — verify against spec choice |
| TC-25 | Same request retried after network timeout (client-side retry simulation) | Client sends request, doesn't receive response, retries with same key | Simulate: call reserve once, then call again with identical key | Second call is a no-op returning first result; only one reservation exists in DB |
| TC-26 | Concurrent duplicate requests with the same idempotency key | Two threads submit simultaneously with identical key | Fire both at once | Only one reservation/order created; the other resolves to the same order id (no race creating two orders for one key) |
| TC-27 | Different idempotency keys, same user/item/qty | User sends two separate legitimate purchase attempts with different keys | Call twice with keys `K1`, `K2` | Two independent reservations are created (each subject to per-user limit checks separately) |
| TC-28 | Missing idempotency key header | Request omits `Idempotency-Key` | Call reserve endpoint | Rejected `400 BAD_REQUEST` (header required) |

## 5. Concurrency / Overselling Prevention

| ID | Title | Preconditions | Steps | Expected Result |
|---|---|---|---|---|
| TC-29 | N concurrent users, demand exactly equals stock | `totalStock=50`; 50 users each reserve qty=1 concurrently | Fire all 50 requests simultaneously | All 50 succeed; final `reserved+sold = 50`; `available()=0` |
| TC-30 | N concurrent users, demand exceeds stock (core anti-oversell test) | `totalStock=50`; 500 users each reserve qty=1 concurrently | Fire all 500 requests simultaneously | Exactly 50 succeed, 450 receive `SOLD_OUT`; final `reserved+sold` never exceeds 50 |
| TC-31 | Concurrent requests with varying quantities | `totalStock=50`; users request random qty 1–5 concurrently | Fire concurrently until oversubscribed | Sum of successful reservations' quantities ≤ 50; no negative `available()` ever observed |
| TC-32 | High-concurrency single-unit item ("last item" contention) | `totalStock=1`; 100 users reserve qty=1 concurrently | Fire all 100 | Exactly 1 succeeds; 99 rejected `SOLD_OUT` |
| TC-33 | No lost updates under concurrent reserve + concurrent release (expiry sweep running simultaneously) | Mixed load: some reservations expiring while new reservations are being made | Run sweeper and reserve calls concurrently for several seconds | Stock counters remain internally consistent at every point (`reserved+sold ≤ total`); no negative values |
| TC-34 | Repeated run stability (flakiness check) | Same as TC-30 | Run the 500-vs-50 scenario 20 times in a row (or via parameterized/repeated test) | Passes all 20 runs with identical invariant (`success count == 50`) — guards against intermittent race regressions |

## 6. Order Lifecycle & Payment Confirmation

| ID | Title | Preconditions | Steps | Expected Result |
|---|---|---|---|---|
| TC-35 | Successful payment confirms order and reservation | Order `PENDING_PAYMENT`, reservation `HELD` | Trigger payment confirmation for the order | `order.status=PAID`; `reservation.status=CONFIRMED`; `item.soldStock += qty`; `item.reservedStock -= qty` |
| TC-36 | Payment confirmation for already-paid order (duplicate webhook) | Order already `PAID` | Trigger payment confirmation again | No double-increment of `soldStock`; operation is idempotent/no-op on second call |
| TC-37 | Payment confirmation for expired order | Order already `EXPIRED`, reservation already `EXPIRED`, stock released | Trigger late payment confirmation | Rejected/handled gracefully (e.g., order re-opened only via defined exception path, or payment refunded) — must not re-increment sold stock against already-reallocated inventory |
| TC-38 | Payment confirmation for nonexistent order | Random/invalid order id | Trigger payment confirmation | Rejected `404 NOT_FOUND`; no state changes |
| TC-39 | Payment confirmation received right at reservation expiry boundary | Reservation `expiresAt` = now (race between sweeper and payment webhook) | Fire expiry sweep and payment confirmation concurrently for the same reservation | Exactly one outcome wins deterministically (either confirmed sale or expired/released) — no state where both `soldStock` and released stock double-count the same units |
| TC-40 | User cancels order before payment | Order `PENDING_PAYMENT` | User calls cancel | `order.status=CANCELLED`; `reservation.status=RELEASED`; stock returned to `available()` immediately (not waiting for sweeper) |
| TC-41 | Cancel an already-paid order | Order `PAID` | Attempt cancel | Rejected — cannot cancel a paid order via this path (must go through a separate refund/return flow) |

## 7. Reservation Expiry Sweeper

| ID | Title | Preconditions | Steps | Expected Result |
|---|---|---|---|---|
| TC-42 | Expired HELD reservation is released by sweeper | Reservation `HELD`, `expiresAt` in the past | Run sweeper job | `reservation.status=EXPIRED`; `item.reservedStock -= qty`; `order.status=EXPIRED` |
| TC-43 | Sweeper ignores reservations not yet expired | Reservation `HELD`, `expiresAt` in the future | Run sweeper job | No change to reservation/order/stock |
| TC-44 | Sweeper ignores already-CONFIRMED reservations | Reservation `CONFIRMED` (paid), old `createdAt` | Run sweeper job | No change — confirmed reservations are never swept |
| TC-45 | Sweeper processes a large batch without double-releasing stock | 1,000 expired `HELD` reservations exist | Run sweeper job once | Each reservation processed exactly once; total stock released equals exact sum of expired quantities |
| TC-46 | Sweeper running twice concurrently (overlapping scheduled executions) | Same batch of expired reservations; sweeper triggered twice at once (simulating overlapping `@Scheduled` runs on a slow batch) | Run two sweeper invocations concurrently | Stock is released only once per reservation, not twice (no double-credit back to available pool) |
| TC-47 | Order expires alongside reservation | Order `PENDING_PAYMENT` linked to expired reservation | Run sweeper | Order transitions to `EXPIRED` only if it was still `PENDING_PAYMENT` (not if it was already `PAID`/`CANCELLED`) |

| ID | Title | Preconditions | Steps | Expected Result |
|---|---|---|---|---|

| TC-49 | `reservedStock`/`soldStock` never go negative | Trigger release/expire operations against edge-case states (e.g., double release) | Attempt to release stock for a reservation already released | Operation is a no-op or rejected; counters never go below 0 |

## Notes on Execution

- Section 5 (concurrency) and Section 6/7 (lifecycle races) are the highest-priority suite — these are the tests that actually validate the "never oversell" and "never double-count" guarantees the design depends on. Run them against H2 in CI and periodically against the target production DB engine (MySQL/Postgres) since locking/isolation-level behavior can subtly differ between engines.
- Treat TC-30 and TC-34 as release-blocking: any flakiness here indicates a regression back to a read-then-write race condition.
- Fuzz-style tests (TC-48) are best implemented as a property-based/randomized test that runs many iterations rather than a single fixed scenario, since race conditions are non-deterministic by nature.
