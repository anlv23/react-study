Below is a realistic **system design** for a **Flash Sale Module** suitable for a side project that focuses on:

* Heavy database transactions
* Concurrency
* Inventory reservation
* Order creation
* Easy load testing with k6
* Java Spring Boot
* H2 database (for local testing)

This intentionally avoids Redis/Kafka initially so you can first master transaction handling.

---

# Flash Sale System Design

## Functional Requirements

* User buys a product during flash sale.
* Inventory cannot become negative.
* No overselling.
* One order per successful purchase.
* Failed payment releases reserved inventory.
* Reservation expires after 10 minutes.

# Reservation Transaction

Everything below happens inside **one transaction**.

```
BEGIN

SELECT inventory

↓

available >= requested ?

↓

UPDATE inventory

available -= quantity

reserved += quantity

↓

INSERT order

↓

INSERT reservation

COMMIT
```

If anything fails

```
ROLLBACK
```

Nothing changes.

---

# Inventory Reservation Algorithm

```
load inventory

if available < requested

    throw OutOfStockException

available -= quantity

reserved += quantity

save inventory
```

# Prevent Overselling

Use Optimistic Locking.

Inventory

```java
@Version
private Long version;
```

When two users buy simultaneously

```
Inventory

available = 1
version = 5
```

Thread A

```
reads version 5
```

Thread B

```
reads version 5
```

Thread A commits

```
available = 0
version = 6
```

Thread B

```
update
where version = 5

0 rows updated
```

Spring throws

```
OptimisticLockException
```

Retry or return

```
Sold Out
```

# What You'll Learn

This project covers many of the core backend concepts used in real e-commerce systems:

* Transaction management with `@Transactional`
* Optimistic locking (`@Version`) and retry handling
* Preventing overselling under high concurrency
* Inventory reservation and release patterns
* Order lifecycle management
* Scheduled expiration jobs for abandoned carts/orders
* Concurrent load testing with k6
* Clean service-layer design and transactional boundaries

Once this version is stable, the next evolution would be introducing a message broker (such as Kafka) to process order events asynchronously, decouple services, and handle much higher traffic while maintaining consistency.
